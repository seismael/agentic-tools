# Models and efficient operation

## Verify access

Select from models the target can actually call through existing authorized connections. Record exact provider/IDs, authentication status without credentials, supported options, verified limits, and access evidence. Distinguish catalogued, authenticated, and successfully invoked.

A model available to the host may be unavailable to the target. A plan price, codename such as “Astra”, or web subscription does not establish an API ID, compatible endpoint, CLI entitlement, or quota accounting. Verify provider adapter and account route. Do not copy browser tokens, invent OAuth flows, add an API-billed fallback, or buy access to complete a routing table.

Do not hardcode a permanently best model. Preserve the current suitable model and native inheritance unless evidence justifies a change; escalate difficult decisions using an existing authorized route when the likely reduction in failures outweighs its cost. Use the current host model if switching is unavailable; do not claim another model was consulted. Evaluate domain fit rather than using a leaderboard as local evidence.

## Routing

| Demand | Selection criterion | Escalation |
| --- | --- | --- |
| Diagnosis, architecture, conflicting evidence | Strong reasoning/synthesis | Unexplained failure, conflict, consequential uncertainty |
| Bounded building or drafting | Observed quality/usage balance | Meaningful checks repeatedly fail or scope grows |
| Mechanical/small edits | Fast suitable model or deterministic tool | Semantic ambiguity or quality failure |
| Validation | Deterministic checks first, judgment where needed | Unresolved high-impact concern |
| Creative exploration | Brief adherence, useful diversity, modality | Repetition or audience/voice mismatch |

Use supported effort for complexity. High effort everywhere can waste resources; weak diagnosis can create rework. Do not force unsupported temperature/token options. More modes need not mean more models. Define rate-limit behavior as wait, checkpoint/stop, or an already approved fallback. Never silently switch subscription work to metered API usage.

## Objective and measurement

Minimize total resources **per accepted outcome** subject to quality and latency/budget limits. Count retries, failed attempts, reviews, auxiliary agents, compaction, schemas/results, repeated handoffs/context, and reasoning where reported. Smaller models are not necessarily cheaper after rework.

Subscription quota, API money, tokens, and elapsed time are different measures. Report counters and verified pricing separately. Deduplicate parent totals that already include subagent usage; distinguish input, output, cached, and reasoning tokens where exposed. Do not convert tokens to dollars or subscription depletion without evidence. Mark unavailable attribution explicitly. Separate one-time characterization cost from recurring execution overhead and savings.

For a bounded before/after comparison, hold tasks, source snapshot, criteria, and environment constant. Prefer a typical task and a difficult case. Compare acceptance/quality, input/output/cached/reasoning tokens where exposed, retries, calls, latency, and interruptions. Small samples provide local evidence, not universal optimality or guaranteed savings.

## Low overhead

- Keep durable conventions short; load domain references and skills on demand.
- Investigate major recurring waste first: verbose generated output, repeated context, broad tool payloads, duplicate research, failed attempts, and unnecessary orchestration. Short final prose alone does not prove low total usage.
- Keep full interviews, evidence, backups, and traces outside automatic context.
- Remove redundant global/project/agent instructions only after ownership and effects are clear.
- Use targeted searches and bounded outputs; retain relevant error and verification evidence.
- Select necessary tools/MCPs; inspect overlap and startup hooks before adding more.
- Prefer deterministic formatting, tests, calculation, and transformations when available.
- Match structure to the consumer: concise actionable prose for people, validated schemas for machine consumers. Preserve decision evidence, actionable errors, required detail, and useful progress; avoid repeated plans, tool narration, and success summaries.
- Add subagents only when concrete benefit exceeds context/review costs; no mandatory committee.
- Preserve decisions, constraints, and authorization in compact handoffs. Do not reset context just to shrink a counter while losing caching or useful state.
- Avoid aggressive compaction or tiny step limits without evidence that work still completes.

Do not add continuous LLM evaluation or telemetry proxies by default. Diagnose on demand from existing logs. Characterize is for configuration and maintenance, not an extra layer on every normal task.

## Research, review, and automation

Define the question, evidence needed, uncertainty to resolve, and stop condition before research. Reuse current primary evidence; expand only for gaps or contradictions that affect the decision. Bound review to changed scope and material failure risks. Report each finding with consequence, evidence, and action instead of a generic checklist.

For requested automation, specify trigger, owner, data/action scope, cost limit, idempotence, duplicate/concurrent execution handling, bounded retries, checkpoint, failure visibility, and cancellation. Prefer deterministic native hooks for mechanical work. Keep unsupported fields as design requirements, not invented config keys. Do not activate new scheduled or model-calling work merely because it is configurable.
